# 项目文档写作规范（Docs Style）

与 `academic-paper` / `academic-pipeline` 配合使用，作为项目本地补充。

## 适用范围

本规范适用于**所有项目文档写作**，取决于用户要写什么：

- 学术论文（`paper/`）：中英术语 / GB·T 7714 / 消融实验
- 技术说明 / 设计文档 / 报告（`docs/`、`project_docs/`、`code/src/DESIGN.md`）
- 交接文档 / 经验记录 / 周报

**通用原则**（证据校验、术语统一、写作语言、自检）适用于所有类型；**论文专属规则**（引用格式、消融实验）在论文场景启用。

## 写作风格（总纲）

**以核心贡献为中心、以自然中文为主要表达、以证据和结构控制篇幅的学术写作风格。**

### 结构与叙事

- **贡献导向**：全文围绕一个明确亮点展开，背景、方法、实验和结论都服务于核心问题。
- **逻辑优先**：按"问题—原因—设计—验证—边界"推进；叙事采用"研究背景—现实问题—解决思路—方法设计—实验效果"自然展开，避免模块罗列和流程流水账。
- **脉络连贯**：全文避免脉络不清晰、逻辑不连贯、散成一盘。整体有明显主线脉络，重点突出，结构前后呼应——引言提出的问题在方法中解决、在实验中验证、在结论中收束。
- **标题层级**：清晰自然，避免生硬、夸张或过度包装。

### 语言表达

- 使用简洁、自然、准确的学术语言，少用生僻术语、工程黑话和内部编号；避免口语化、宣传式和防御性表述。
- 删除重复解释、辩解式表述和过多限定条件；必要的范围说明直接陈述。
- **冒号克制使用**：论文正文一段话中间不轻易用冒号"："，读起来突兀。冒号只保留在确有必要的场合（摘要结构、图题表题、总起句后列举例证）；普通行文中的解释、递进、转折改用逗号、句号或"即""也就是""包括"等自然衔接。
- 摘要保持适中长度：既不精简过头也不堆砌细节。
- 背景交代清楚但避免铺陈。

### 内容分配

- 区分普遍问题与本文具体问题，不扩大论断范围。
- 贡献强调方法和创新点，结论集中呈现最终结果，避免两部分重复。
- 结果集中：具体数字主要交给表格，正文强调趋势、比较关系和科学含义，避免逐项复述。

### 方法、证据与边界

- **方法清晰**：突出设计机制、控制变量、评价标准和适用边界；工程参数只保留影响可复现性和有效性的部分。
- **证据匹配**：论断强度与实验结果相匹配，不夸大结论；区分主实验、消融实验、探索性分析和边界分析。
- **诚实但不防御**：对局限性和适用范围保持诚实，但避免写成防御性声明（不写"本文不声称 / 本文仅"）。

### 图表

- 图表各自承担明确功能：总图讲整体机制，分图讲关键局部；图注说明图的作用和实验条件，不重复正文。
- 图表突出单一重点，避免信息过载、装饰过多和无效比较。
- 图形偏好简洁、克制、低饱和，整体保持黑白灰或统一配色。
- 实验内容优先用图表呈现，正文只解释关键指标和主要结论。

### 术语

- 优先使用中文，英文只在首次定义、专业缩写或专有名词确有必要时出现；全文统一（对照术语表）。

### 结论

- 按"核心机制—解决问题—主要结果—适用边界—未来工作"收束全文。

### 文献

- 优先引用近期、相关性强、层次较高且真正支撑论点的工作；重视真实性、引用对应关系和时效性；经典文献保留，关系弱或过时的文献删减。

**总体追求**：信息密度高、主线突出、读者一遍能够理解——逻辑清楚、语言自然、重点突出、数据简洁、图表克制，避免堆砌术语、重复解释和工程化表达。

## 一、证据强制校验（写任何文档前必须做）

**写任何声明前，先校验证据；证据不足不写，宁可标注也不编造。**

1. 每个实验 / 数据 / 数字必须能追溯到 `project_docs/evidence/` 中的证据包或具名基线。
2. **禁止编造**实验、数据、引用、结果——这是不可逾越的红线。
3. 无法核实的引用或数据，标注 `[待核]` 并列出待办，不进入最终正文。
4. 证据分级：已读原文 / 已读摘要 / 仅有元数据 / 待核验。只有前两级可作结论依据。

## 二、引用核查（引用前逐条核对）

1. 每条引用尽量定位到原文（页码 / 章节）。
2. 区分**直接引用**（逐字，超长加引号）与**间接引用**（转述）。
3. 拒绝三类错误：幽灵引用（引用了但原文不存在）、转引错误（引二手非原始）、断章取义。
4. 数据引用精确到数据库名、变量名、样本时间范围。
5. 输出核查结果：已核实 / 待核 / 无法核实，诚实标注。

## 三、引用格式（论文场景：GB/T 7714）

1. 论文参考文献按 **GB/T 7714-2015** 著录；全文统一。
2. 中英文文献、期刊 / 会议 / 学位论文条目格式符合国标。
3. 正文引用标注与文末文献表一一对应，无孤立引用。
4. 技术文档引用从简但必须真实、可溯源。

## 四、格式自检清单（交付前逐项过）

- [ ] 每个数字都能指向证据包 / 基线
- [ ] 无编造实验、数据、引用
- [ ] 术语统一（`docs/GLOSSARY.md`；论文场景还须中英对照）
- [ ] 引用真实可溯源（论文场景 GB·T 7714）
- [ ] 全角中文标点，中英文间无多余空格
- [ ] 图表只保留支撑论点的指标
- [ ] 数字口径标明：软件复现 / 策略复现 / RTL 回放 / 工具报告 / 实测

## 五、写作语言

- 中文优先；正文写成成熟文档，不写版本迭代、开发过程或防御性说明。
- 避免 AI 套话：禁用机械过渡词（首先 / 其次 / 此外）、空壳强调句（值得注意的是）、空洞修饰词。
- 用语义衔接替代模板衔接，用数据事实替代形容词。

## 六、历史版本数据的使用（论文场景：消融实验）

1. **正式结果用最新版本**：论文主结果、主结论一律基于最新版本（当前活跃基线）的数据。
2. **历史版本数据 → 消融实验**：旧版本 / 历史配置的数据可用于**消融实验或对比分析**，以支撑某设计决策。
3. **不写"版本"字眼**：正文不出现"版本 1 / 旧版本"等开发性表述；消融变体用**功能差异命名**。
4. **数据真实**：数字来自对应版本 / 配置的真实证据包，交叉表记录。
5. **口径可比**：消融对比与正式结果的运行条件、输入、样本需一致可比。

## 七、术语同步

- 修改任何文档时若术语 / 译名 / 缩写改变，**必须同步更新**术语表：`docs/GLOSSARY.md`（项目级），论文场景还须更新 `paper/GLOSSARY.md`（中英两版）。
- 顺序：先改术语表，再改文档（或同一编辑内完成）；定稿时核对无旧译名残留。

## 八、审稿工作流（多智能体 + 多 skill）

审稿迭代时**调用多智能体**，每个智能体用不同的审稿 skill 独立审稿，讨论综合后修改。

**项目审稿 skill**：

| skill | 视角 |
|-------|------|
| `nature-reviewer` | 审稿人视角独立评审 |
| `academic-paper-reviewer` | 7-agent 同行评审模拟 |
| `nature-ref-verifier` | 引用真实性核查 |
| `nature-response` | 审稿回复组织 |
| `chinese-paper-style` | **项目写作风格（最高优先级）**：格式 / 术语 / 摘要 / 结论 / 红线 |

**优先级**：`chinese-paper-style`（本项目写作风格）**最高**——其他审稿 skill 的发现都要对照它过滤；与本项目写作风格冲突的修改，优先按 `chinese-paper-style` 执行。

**流程**：

1. **多智能体并行审稿**：派发多个智能体，各用不同 skill 独立审稿（如 A→`nature-reviewer`，B→`academic-paper-reviewer`，C→`nature-ref-verifier`，D→`chinese-paper-style`）。
2. **收集意见**：汇总各智能体发现（缺陷 / 澄清 / 建议），标注来源 skill；**先按 `chinese-paper-style` 过滤**（写作风格相关意见优先）。
3. **讨论综合**：对照意见找共性与分歧，综合成一份审稿行动清单。
4. **修改**：按「优先补实验 / 完善设计，而非降级描述」处理（见 `paper/zh/responses/RESPONSE_TEMPLATE.md`）。
5. **每轮归档**：建 `paper/zh/review_rounds/r<N>_<日期>/`，归档该轮意见、回复、修改前论文。
6. **一致性检查**：术语 / 证据 / 交叉表，再写回复（`nature-response`）。

**多角度分轮审稿**：每次审稿聚焦**一个方面**，即使该角度通过也换下一个角度再审，直到覆盖全部角度：

| 轮次 | 审稿角度 |
|------|----------|
| ① | 语言学术化（规范术语、避免口语 / 机械套话） |
| ② | 自信 / 去保护性语言（无"本文不声称 / 本文仅"） |
| ③ | 摘要（四要素、简洁、第三人称） |
| ④ | 结论（机制 → 问题 → 结果 → 边界 + 一句未来工作） |
| ⑤ | 引言（漏斗聚焦、面向大同行） |
| ⑥ | 相关工作（讲别人 → 引出 → 再讲本文） |
| ⑦ | 术语（业界译名、防直译、统一、术语库同步） |
| ⑧ | 章节亮点（避免技术说明书） |
| ⑨ | 图表（数据来源、格式、与论文数字一致） |
| ⑩ | 证据 / 数字（可追溯、口径、交叉表） |
| ⑪ | 红线（版本代号 / 过程性语言 / 路径 / 保护性） |
| ⑫ | 格式（期刊规范、GB/T 7714、图表规格） |
| ⑬ | 脉络连贯（整体主线清晰、重点突出、前后呼应、不散盘；引言问题 → 方法解决 → 实验验证 → 结论收束） |

规则：每轮**一个角度**聚焦审查；**通过也换角度**再审；全部角度覆盖后再跑最终一致性检查。

## 九、绘图分工

| 图类型 | 由谁画 | 方式 |
|--------|--------|------|
| 数据图（定量折线图、统计图、曲线） | AI 用 `nature-figure` 技能 | 脚本生成，数据来自证据包，**可复现** |
| 机制图（系统结构图、流程图、硬件结构图） | **详细设计提示词（结构示意）→ 草图 → 用户手工画最终版** | AI 给出含结构示意的提示词 + 草图，用户按提示词绘制 |

- 数据图 → `paper/zh/figures/data/`：必须可复现（脚本 + 数据源），按 `nature-figure` 规范；**默认输出最清晰格式**（SVG / PDF 矢量 + 高分辨率 PNG ≥300 dpi）；**每张图填数据来源记录**（`data/plot_specs/DATA_SOURCE_TEMPLATE.md`，含基线/配置/口径），定稿存 `data/final/`。
- 机制图 → `paper/zh/figures/manual/`：AI 先写**详细设计提示词**（见 `manual/drawing_prompts/MECHANISM_FIGURE_PROMPT_TEMPLATE.md`，含模块 / 连线 / 数据流 / 层次结构示意），并出草图放 `manual/figures/`；论文中放草图占位，**最终由用户按提示词手工绘制**，源文件与定稿都存 `manual/figures/`。

## 十、写作红线：版本代号 / 过程性语言 / 保护性语言

论文正文**禁止**：

1. **工程版本代号**：`v1.0 / v2.0`、基线 ID（如 `R3-20260731`）、审稿轮次（`r1 / r2`）、commit hash、迭代编号——正文一律不出现；**不与以前版本做对比**。
2. **过程性语言**："我们修改了 / 改进了""第一版 / 后续版本""开发中 / 迭代中""这轮 / 上轮""重构后 / 修复后"——用结果性、静态的表述替代。
3. **文件路径**：`project_docs/evidence/...`、`experiments/...`、`code/...` 等工程路径——**论文正文一律不写**。论文数字与证据的路径映射统一在单独文件（`project_docs/evidence/CROSSWALK_TEMPLATE.md` 交叉表）记录，论文只写数字 / 结论。
4. **保护性 / 防御性语言**：不写"本文不声称…""本文仅…""本文不试图…""我们并不认为…"等自我设限的辩护；用**陈述性、自信**的口吻呈现结果与结论。**边界用客观陈述**（如"适用于 XX 条件"），而非谦逊辩护。

**替代方式**：

- 用**功能 / 设计差异**描述不同实现（如"含反馈回路的版本"→"带反馈回路的设计"），不用版本号。
- 用"**所提方法 / 系统 / 框架**"指代最终方案，不用"我们之前的版本"。
- 呈现的是**最终成熟结果**，不叙述开发过程、修订历史或迭代。
- 涉及不同配置 / 消融对比时，用**配置 / 特性命名**（`w/o 模块A`、`baseline-XX`），不用版本号。

## 十一、术语审查（业界译名 + 防直译）

中文论文术语审查是重点，尤其针对**业界有认可英文词汇**的技术术语：

1. **业界认可译名**：技术术语优先采用业界 / 期刊 / 标准认可的中文译名（对照 `paper/GLOSSARY.md`、参考文献、GB/T 标准），不自行生造。
2. **防生硬直译**：逐句检查全文是否有**生硬直译**——英文概念直译成中文后别扭、不通顺或不专业（如 golden implementation 直译"金牌实现"），改为规范通顺的译法。
3. **审查时机**：每次论文修订 / 审稿时，**全文扫查**英文术语与直译情况。
4. **修正同步**：修正译名后同步术语表（先改表再改正文，见第七节），中英两版一致。
5. **配合语境斟酌**：翻译配合语境——同一英文概念在不同语境下可能需用不同中文表达（视上下文强调角度、搭配通顺度），结合语境选最贴合含义 / 最通顺的译法；核心专有术语仍保持全文统一（见第七条）。
6. **中译英同样审查**：中文论文转英文时，同样逐条审查——中文术语用**业界认可的英文标准术语**（对照 `paper/GLOSSARY.md` 英文列、参考文献、IEEE/ACM 通用用语），不机械直译中文；术语检查清单对中英两版都适用。
7. **术语库维护是关键**：术语审查的准确性依赖术语库（`paper/GLOSSARY.md` 中英对照 + `docs/GLOSSARY.md` 口径）。维护要求：
   - 新增术语及时登记（含业界认可译名、缩写、解释、**中英双向对照**）；
   - 审查中确定的译名**写回术语库**，避免下次重审；
   - 中译英 / 英译中都有依据；
   - 定期核对业界 / 期刊认可的译法。

**审稿时的术语检查清单**：

- [ ] 英文技术术语是否用业界认可中文译名
- [ ] 全文是否有生硬直译（读起来别扭的）——逐个修正
- [ ] 同一概念全文是否统一译名
- [ ] 修正后是否同步 `paper/GLOSSARY.md`

## 十二、摘要写作（四要素 + 怎么写）

研究论文摘要**四要素**，整体约 150~250 字，第三人称：

| 要素 | 长度 | 句式 / 怎么写 | 不写什么 |
|------|------|--------------|----------|
| ① 目的 | 1~2 句 | "针对【问题】…"（点出要解决的痛点） | 宽泛背景（引言才写） |
| ② 方法 | 1~2 句 | "所提【方法】提出 / 设计 / 采用【核心机制】…"（本文提出什么） | 实现细节 / 模块清单 |
| ③ 实验 | 1~2 句 | "在【平台 / 数据集】上，与【对比】相比…" | 实验过程细节 |
| ④ 结果 | 1~2 句 | "【指标】提升至【数值】，【指标】降低【比例】" | 无结果的空泛表述 |

规则：

- **各要素精简**：目的 / 方法各 1~2 句；实验 + 结果合计 2~3 句。
- 不用第一人称（"所提方法 / 算法 / 模型"）。
- **缩写给全称**：摘要中首次出现的缩写（含方法 / 系统名等）给出全称——"中文全称（缩写）"或"缩写（English Full Name）"，如"所提方法提出失效驱动候选生成引擎（Failure-Aware ECO, FAECO）"；正文后续直接用缩写。
- 中英摘要一一对应。
- 数字有依据（证据包 / 交叉表可追溯）。
- **常见错误**：写成引言（背景过多）、写成方法细节、没写结果、用第一人称、过长。

**示例**：

> 针对【高速流分类吞吐受限】的问题，所提方法采用【快慢路径分离架构】，将缓存命中请求置于流水线快路径处理，未命中转慢路径匹配。在【100 Gbps 平台】上与现有方案相比，所提方法将分类吞吐提升至【102.35 Gbps】，平均时延降低约【30%】。

- 综述论文摘要另见模板说明（"介绍了…""指出了…"句式）。

## 十三、结论写作（机制 → 问题 → 结果 → 边界 + 一句未来工作）

结论**不是"做了哪些模块、跑了哪些实验"的流水账**，而应回答三问：

1. **机制与问题**：本文设计靠**什么机制**解决了**什么问题**。
2. **结果与效果**：这些机制带来了什么**结果**、效果多好（关键指标）。
3. **边界**：方法的**适用边界 / 局限**在哪里。

规则：

- 不按"模块清单 + 实验流水账"收束。
- 简洁（结果 + 结论），结尾**一句简短未来工作**（期刊要求）；不写具体展开的下一步计划。

**示例写法**：

- 好：所提方法以【XX 机制】为核心，解决了【XX 问题】；在【XX 场景】下将【指标】提升至【数值】，适用边界为【条件】。未来工作将扩展至 XX 场景。
- 避免：系统由模块 A、模块 B、模块 C 组成；实验在数据集 1、数据集 2 上运行；未来工作将优化 XX、引入 XX、支持 XX。

## 十四、引言写作（大领域 → 小领域聚焦 + 面向大同行）

引言结构**从大到小聚焦**（漏斗式），让大同行能看懂：

1. **大领域背景**：从宽泛的大领域讲起（该领域的重要性与广泛影响）。
2. **收窄到子领域**：逐步聚焦到具体子领域 / 方向。
3. **具体问题**：指出该方向尚未解决的痛点 / 挑战。
4. **现有工作不足**：简要说明已有方法局限（配引用）。
5. **本文方法**：引出所提方法 / 系统，说明如何解决。

规则：

- **面向大同行**：背景铺垫充分、由浅入深，领域外读者也能理解；必要术语首次出现时解释。
- 引言不加章节号、不插图表格公式、不用结论性表述。
- 与摘要、结论不重复（背景与问题 → 方法，不含结果）。

## 十五、相关工作写作（讲别人 → 引出问题 → 再讲本文）

相关工作**不是每个都要和本文对比**：

1. **讲相关工作**：按主题组织，客观介绍已有方法 / 研究（配引用）。
2. **引出问题**：指出相关工作**尚未解决**的问题 / 局限（为本文铺垫）。
3. **本文设计**：相关工作讲完后，统一引出本文设计 / 与已有的区别。

规则：

- **讲别人工作时不穿插"本文…"**：相关段落专注讲已有工作及其局限，不提前讲本文。
- 本文设计 / 对比放在相关工作**最后统一引出**（或单独小节）。
- 只对**关键相关**（直接影响本文设计的）做明确对比，不必每个都对比。

## 十六、章节标题与亮点导向（避免技术说明书）

1. **章节标题用设计亮点**：用核心机制 / 创新点命名章节（如"失效驱动候选生成机制""快慢路径分离架构"），不用"系统设计""方案设计"这类泛化标题。
2. **避免技术说明书**：正文突出**设计决策与为什么**（创新点、权衡、边界），不是平铺直叙的功能 / 模块清单。
3. **章节体现贡献**：每个章节标题应能让读者看出本文的贡献点。
4. **结构逻辑**：围绕**核心机制 / 创新点**组织，而非按"输入-处理-输出"说明书式组织。

## 十七、图表注释（简洁 + 不与正文重复）

1. **注释简洁**：图题 / 表题 / 表注 / 图表内文字精炼，只放必要信息。
2. **不与正文重复**：图表注释**不重复正文已说明的内容**——解释性、分析性内容放正文；图表只承载数据 / 结构本身 + 必要标注。
3. **图题 / 表题**：简短，标明图表是什么；无句末标点。
4. **表注**：只补充必要信息（如粗体含义、缩写解释、数据来源），不重复正文。
5. **自明而不赘述**：图表看图能懂，但解释交给正文——注释不替代正文分析。

对照期刊模板：图题和分图题应精炼，解释性词语放入正文，图题中一般不加标点符号。

## 十八、写作流程（先框架确认 + 数据完备前提）

**写论文 / 其他文档前，先写框架，用户确认后再写正文。**

1. **先出框架**：写正文前，先产出文档框架 / 大纲——每部分准备写什么（标题 + 要点 + 用哪些数据 / 图表），提交用户确认。
2. **用户确认后写**：框架确认后再展开正文；**不跳过确认直接写**。
3. **数据完备前提**：写论文前，确认所需**数据 / 实验 / 证据已完备**（查 `project_docs/evidence/EXPERIMENT_REGISTRY.md` + `evidence/`）——避免半路补实验、反复改设计。
4. **数据缺失时**：先补实验 / 完善设计，再动笔（优先补强而非降级）。
5. **实验记录规范**：实验过程与结果**记录齐全、分类清晰**（配置与结果一一对应、按实验归档，见 `experiments/README.md`），写论文时能直接定位证据；避免因记录缺失反复重跑实验，避免不同配置 / 版本的结果弄混。

## 十九、论文文件命名（按标题命名）

**论文源文件与编译产物 PDF 一律用论文标题命名**，不用 `example_paper` / `template` 等通用名：

1. **源文件**：`manuscript/` 下的 `.tex` 文件名 = 论文标题（如 `面向高速流分类的快慢路径分离架构.tex`）。
2. **编译产物**：编译命令用同名（`compile.ps1 -Name <标题名>`），`build/` 与 `paper/zh/` 根目录的 PDF 同名输出，方便直接按标题查找最新稿。
3. **中文文件名兼容性**：中文标题可直接作文件名；若 LaTeX 编译链（Windows PowerShell + LuaLaTeX）对中文文件名报错，则用与标题对应的英文短名（如 `fast-slow-path-separation.tex`），并在 `paper/zh/README.md` 记录"文件名 ↔ 论文标题"对应关系。
4. **改标题时同步改名**：论文标题定稿 / 修改后，同步重命名源文件、重新编译，删除旧名产物，避免同名不同稿。
