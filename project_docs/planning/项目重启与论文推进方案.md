## 3. 项目主题解析

### 3.1 大背景

ECO（Engineering Change Order）用于芯片设计后期的功能错误修复和时序违例修复。现有材料围绕三个核心矛盾展开：

1. 设计后期不能大规模重跑物理设计流程，只能做小范围增量修改。
2. 功能修复和时序修复长期割裂，功能补丁可能引入时序问题，时序优化也可能破坏功能等价性。
3. 传统 buffering、gate sizing 和 remapping 在严重违例、有限 spare cell、复杂物理约束下能力不足。

### 3.2 现有 RSECO 基础

学长工作 RSECO 的主线是“基于重综合的掩膜前时序 ECO 框架”。核心思想是：利用重新综合得到的新网表，通过等价点匹配、关键路径感知切割和网络流最小割，把新网表中时序更优的局部子电路移植到旧网表中，从而修复严重 setup timing violation，同时尽量保持原版图稳定。

这条线的优势是论文结构完整、方法边界清楚、实验指标明确。缺点是现有源码遗失，且如果完全复刻 RSECO，创新性可能不足，除非找到新的改进点。

### 3.3 当前最有价值的研究空白

从现有材料看，最值得继续推进的空白不是泛泛地做“AI + ECO”，而是选择一个可闭环验证的狭窄问题：

1. **功能-时序协同 ECO**：把功能等价性验证和时序改善放到同一个优化闭环里。
2. **形式化验证约束下的 LLM/RL ECO patch 搜索**：让智能方法负责候选生成，让 SAT/ABC/OpenSTA 负责裁判。
3. **RSECO 的智能化扩展**：保留 RSECO 的等价切割/替换思想，在候选 patch 选择、切割权重调整或关键路径排序上引入学习方法。

## 4. 推荐主线选择

### 4.1 不建议直接做的路线

不建议一开始就做“完整功能-时序-物理三者联合的 GNN+RL 大系统”。该方向故事强，但工程跨度过大：需要 Verilog/Yosys/ABC/OpenSTA、图学习、强化学习、数据生成、baseline 复现和论文实验同时成立。一旦任何一环不稳定，论文会很难收敛。

也不建议第一阶段做 post-mask spare cell 级真实工业 ECO，除非奇捷或其他合作方能稳定提供平台、真实网表、约束、可复现实验环境和授权。否则数据和工具链会成为主要风险。

### 4.2 推荐主线 A：RSECO 重建 + 智能候选选择

这是最稳妥的论文路线。目标不是复刻旧代码，而是重建一个可复现的 RSECO-style ECO 框架，并加入一个清晰的新贡献：用学习或启发式评分改进 patch/cut 选择，使其在严重时序违例下比传统局部修复更容易收敛。

核心问题：在新旧网表之间存在多个可替换等价子图时，如何选择一个既改善时序、又减少改动范围、且保持功能等价的 patch。

可发表贡献：

1. 一个开源可复现的 RSECO-style 掩膜前时序 ECO 实验流程。
2. 一个关键路径感知的候选 patch 生成与排序方法。
3. 一个基于 ABC/SAT 和 OpenSTA 的功能-时序双验证闭环。
4. 在 ISCAS/ITC/EPFL 等 benchmark 上给出 WNS/TNS、修改规模、运行时间、成功率对比。

### 4.3 推荐主线 B：形式化验证闭环的 LLM 功能 ECO Demo

这是最快能做出 demo 的路线。先做小规模 gate-level functional ECO：LLM 生成 patch，Z3/ABC 验证，失败时用 counterexample 反馈修正。

核心问题：在有限 gate library 或 spare cell 约束下，如何自动生成功能等价的逻辑补丁。

优点：工程量小，6-8 周内有望完成可展示系统。缺点：如果只停留在小布尔函数，容易被认为 toy；需要扩大到真实 gate-level cone，并加入和 ABC/Yosys baseline 的比较。

### 4.4 推荐主线 C：功能-时序协同 ECO 长线版本

这是最终论文冲击力最高的路线，但应作为主线 A/B 成功后的扩展，而不是第一阶段起点。可在已有 patch 搜索闭环上加入 OpenSTA，要求 patch 不仅功能等价，还要满足 slack 改善或至少不恶化。

## 5. 建议采用的阶段路线

### Stage 0：工程重建基础

目标：恢复可持续开发能力，而不是直接写算法。

必须完成：

1. 在工作区初始化 Git 仓库。
2. 建立标准目录：`src/`、`tests/`、`data/`、`benchmarks/`、`experiments/`、`docs/`、`paper/`。
3. 固定 Python 环境和依赖管理文件。
4. 建立最小 CI 或本地验证脚本。
5. 所有实验输出写入 `experiments/YYYYMMDD_*`，保证可追溯。

验收标准：能运行 `pytest` 或等价测试命令，能用一条命令跑通最小 demo。

### Stage 1：最小功能验证闭环

目标：先跑通“候选 patch -> 等价性验证 -> 失败反例 -> 重新生成/搜索”的闭环。

技术构成：

1. 布尔表达式或小型 Verilog cone 解析。
2. Z3 或 ABC 做等价性验证。
3. patch 表示格式：JSON 或简单 gate netlist。
4. baseline：穷举搜索、ABC rewrite/remap、手工启发式。

验收标准：在 20-50 个小规模逻辑修改案例上输出成功率、验证时间、patch size。

### Stage 2：接入真实 gate-level benchmark

目标：从 toy function 过渡到真实电路子图。

推荐数据：

1. ISCAS'85 / ISCAS'89 小中规模电路。
2. EPFL combinational benchmark。
3. ITC'99 中较大规模时序电路作为后续扩展。

必须实现：

1. Yosys 统一综合到 gate-level netlist。
2. 从目标节点提取 fanin/fanout cone。
3. 构造故障或变更：gate replacement、signal inversion、logic mutation、constraint-driven resynthesis。
4. ABC/SAT 验证 patched cone 与 golden cone 等价。

验收标准：至少 5 个 benchmark、每个 benchmark 多个变更实例，形成结构化实验表。

### Stage 3：加入时序目标

目标：把论文从“功能 patch”推进到“功能-时序协同 ECO”。

必须实现：

1. OpenSTA 读取 netlist、library、SDC。
2. 提取 WNS/TNS、关键路径、节点 slack。
3. patch 选择时加入 timing score。
4. patch 后重新 STA 验证。

验收标准：对比 “只保证功能等价” 与 “功能等价 + 时序感知选择” 的 WNS/TNS、面积和成功率差异。

### Stage 4：论文实验闭环

目标：让实验足以支撑论文主张。

实验至少包含：

1. 功能修复成功率。
2. 时序改善：WNS/TNS/违例路径数量。
3. 代价：修改门数、面积估计、运行时间。
4. 消融：无 timing score、无 counterexample、无 patch ranking 等。
5. 可扩展性：随 cone size、benchmark size、候选数量变化的趋势。

### Stage 5：论文写作与投稿

目标：形成可投论文，而不是工程报告。

建议论文叙事：

1. 背景：ECO 后期修复需要小范围、可验证、可收敛的增量修改。
2. 缺口：现有方法多把功能修复和时序修复分开处理；智能方法缺少形式化验证约束。
3. 方法：提出一个 verification-in-the-loop 的功能-时序协同 ECO 框架。
4. 证据：在公开 benchmark 上同时证明功能正确、时序改善、修改规模可控。
5. 结论：智能搜索只有在形式化验证和 STA 闭环约束下，才适合进入 ECO 场景。

## 8. 风险与控制

| 风险 | 影响 | 控制策略 |
|---|---|---|
| 源码遗失 | 无法复现旧工程 | 不再依赖旧实现，按论文目标重建最小闭环 |
| 方向过大 | 工程长期不收敛 | 先做功能验证闭环，再加入时序，不一开始做完整 GNN+RL |
| 工具链复杂 | Yosys/ABC/OpenSTA 安装和格式转换耗时 | 每接入一个工具就写 wrapper 和最小测试 |
| 论文创新不够 | 难投高水平会议 | 避免只复刻 RSECO，必须加入新的协同验证、patch ranking 或智能搜索机制 |
| 实验不够真实 | 审稿人认为 toy | 先小例子验证，再扩展到公开 benchmark 的真实 cone |
| LLM 不稳定 | 结果不可复现 | LLM 只作为候选生成器，最终结果必须由 SAT/ABC/OpenSTA 验证；同时保留非 LLM baseline |

## 9. 投稿定位

短期目标应先形成 workshop / 中文核心 / 领域会议可交流版本；中期目标再冲 EDA 主流会议或期刊。

| 档位 | 目标 | 条件 |
|---|---|---|
| 第一档 | DAC / ICCAD / ASP-DAC | 真实 benchmark、强 baseline、明显时序收益、完整消融 |
| 第二档 | DATE / TCAD / Integration | 方法扎实、实验完整、工程可复现 |
| 阶段性 | MLCAD / ISPD workshop / 国内会议 | demo 成熟、有初步实验和清晰问题定义 |

## 10. 当前推荐决策

建议立即采用“双层路线”：

1. **短线 6-8 周**：完成形式化验证闭环的 functional ECO patch 搜索 demo，证明从零重建可行。
2. **中线 3-6 个月**：扩展到 RSECO-style timing-aware patch selection，形成真正论文贡献。
3. **长线 6-12 个月**：加入 GNN/RL/LLM 作为候选排序或策略搜索模块，冲击更强论文。

这个顺序能最大限度降低风险：即使 AI 模块效果不稳定，基础的验证闭环和 ECO benchmark 流程也可以支撑一篇方法/系统类论文；如果 AI 模块有效，则可以升级为“智能功能-时序协同 ECO 框架”。
