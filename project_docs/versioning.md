# 版本管理

## 一个版本 = 什么

版本由**具名基线**定义，是「论文 + 源码 + 测试 + 证据」的绑定，四者必须一致：

| 要素 | 由谁决定 | 存放 |
|------|----------|------|
| 论文 | 基线文档声明的主稿件 | `paper/zh/manuscript/` |
| 源码 | git commit / tag / manifest | `code/src/` |
| 测试 | 随源码演进的测试（与源码同 commit） | `code/tests/` |
| 证据 | 不可变证据包 | `project_docs/evidence/` |

## 版本完整体（self-contained，最高要求）

**每个版本工程目录必须是一个完整独立的整体——零交叉引用、零跨版本依赖。**

1. **完整自包含**：每个版本目录包含该版本所需的全部源码、脚本、配置、约束与说明，不依赖其他版本或公共目录的任何文件。
2. **禁止跨版本引用**：任何版本目录内的文件不得引用其他版本目录（或跨版本共享目录）中的文件，**包括脚本**。
3. **需要即复制**：派生新版本时，把需要的文件**完整复制**进新版本目录；复制后即与本版本绑定，不再引用原文件。
4. **接受少量重复**：即使版本间内容几乎相同，也各自持有完整副本；重复换取的是版本完全隔离——每个版本可独立移动、删除、回退而不影响其他版本。

## 代码多版本怎么管

- **版本历史由 git 承载**：每个 commit = 一个不可变的历史版本，tag 标记里程碑；git 记录版本演进，可随时回到任一历史状态。
- **工程目录是独立副本**：运行 / 构建用的工程目录可以是复制出来的**完整独立副本**（含脚本、配置），每个副本自包含；git 负责历史，副本负责"当前可用的一套完整环境"。
- **冻结版本收进 `versions/`**：每个版本目录为完整体（`code/` + `project/` + `experiments/` + `docs/`），完整复制后自成一体、零交叉引用；开发在根 `code/` 推进，主目录始终为最新版本。
- **冻结基线时**，用 manifest 记录「源码 + 测试 + 证据」的 SHA-256 清单，把四者锁定。

### 测试脚本版本

- 测试随代码在同一仓库演进，属于同一个 commit——**测试永远绑定它所在 commit 的源码**。
- 需要按版本区分时：测试文件内注释标明适用基线，或 `code/tests/` 下按版本分子目录（如 `code/tests/r3/`）。
- 冻结基线时，manifest 把测试文件 hash 一并记录，确保「这段代码用的正是这套测试」。

## 何时新建版本

- 功能门完整通过并**独立验证**后。
- 论文大改（需重新声明基线）。
- 证据重做（新建证据包）。

## 多版本共存

- 旧基线标记 `superseded` 后**不可变**，作为历史参照保留。
- 各版本目录为**完整体、互不引用**；新版本复制派生后自成一体。
- 新基线取代旧基线：先过完整功能门 + 独立验证。
- **禁止**：跨版本引用文件（含脚本）；把旧基线数据拼进新包；用工作树名 / 运行目录名当版本；修改已冻结的证据包。

## Git 同步纪律与版本隔离

1. **阶段性同步**：完成阶段性工作（功能门、实验包、论文一轮）后，立即 `git commit` + `git push`；里程碑成果打 `git tag <基线ID>`，tag 与基线绑定。
2. **先备份再推进**：工程代码在重大改动 / 重构 / 实验切换前，先用 commit 或 tag 固化当前状态再推进，保证任何时刻可回退。
3. **版本隔离**：不同基线相互隔离，不跨版本引用文件；每个基线自包含源码、测试、证据与论文。
4. **版本完整体**：每个版本目录完整自包含；派生新版本时复制完整副本，复制后不引用旧版本任何文件（含脚本）。

## 防乱原则（管理纪律）

版本管理**宁慢勿乱**——任何时刻都能一句话说清「哪个是最新、哪个是历史、哪个在用」：

1. **命名统一**：版本目录、tag、基线 ID 全仓库一套命名规则，不出现 `final` / `new` / `backup` / `copy2` 这类含糊名。
2. **单一声明源**：当前活跃版本只认 `BASELINE_INDEX.csv`（`status=active`）一处声明；其他文档引用版本必须与之一致，发现不一致先修正再干活。
3. **临时备份用 git**：试验性改动走分支 / stash / commit 承载，不在工作树里随手复制 `_bak` / `_new` 目录。
4. **冻结即不可变**：收进 `versions/` 的快照不再修改；要改就派生新版本并登记来源。
5. **派生留痕**：每个新版本的 README 写明「从哪个版本派生 + 改了什么」，版本间关系一眼可查。
6. **及时清理**：合并 / 冻结完成后清理临时分支与过期副本；`git status` 不长期积压未提交改动。

## 版本推进方式（小步推进 + 功能门禁）

版本演进**小步推进、逐步验证**，每一步走得踏实再走下一步：

1. **小步推进**：一次只推进一个功能 / 一处改动，不攒大改动；每步的改动范围一句话能说清。
2. **功能正确性门禁**：每个功能推进前必须过**完整功能门**（编译 / 测试 / 关键场景验证全部通过），门禁不过不进入下一步；不跳门禁赶进度。
3. **逐步验证**：每步完成立即验证本步，不堆到最后一起验；发现问题当场归因修复（归因流程见 `experiments/README.md`），修完再走。
4. **每步留痕**：验证通过即 commit 并注明验证结果，保证任意一步可回退、可追溯。
5. **验收标准前置**：动手前先明确「这个功能怎么算对」（验收标准 / 测试用例），避免边写边改标准。

## 历史版本数据在论文中的使用

- 论文**正式结果**一律基于最新版本（当前活跃基线）。
- 历史版本 / 历史配置的数据可用于**消融实验或对比分析**（支撑某设计决策），但正文不出现"版本 N / 旧版本"等开发性表述，用功能差异命名。
- 详见 `skills/chinese-paper-style/SKILL.md` 第六节。

## 归档

各对象（源码 / 论文 / 实验 / 数据 / 图表 / 文档 / 基线 / 技能等）的**归档时机与位置**，统一见 `project_docs/ARCHIVE_POLICY.md`。

## 版本与 git

- 基线确定后打 tag：`git tag <基线ID>`。
- 分支 / 工作树是**执行环境**，不是版本；只有基线能定义版本。
